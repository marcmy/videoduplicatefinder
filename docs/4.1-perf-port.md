# 4.1 performance port history

`perf/4.1-native-hwaccel` was created to carry the useful native/performance work forward onto the 4.1 application architecture without reviving the old 4.0 GUI fork.

This file is historical. The authoritative current ownership map is [`../FORK_DIFFERENCES.md`](../FORK_DIFFERENCES.md).

## Original 4.1 port sequence

The first meaningful 4.1 performance commits on 2026-07-07 were:

- `a8f906f` — seed the 4.1 native FFmpeg decoder layer.
- `b1d4828` — integrate the native FFmpeg extraction engine.
- `e93ca19` and the nearby native-regression test commits — restore coverage around the ported decoder.
- `ae42461`, `5123643`, `8219f8a`, `e54ce6a`, and `6d32c53` — adapt the separate CPU matching-headroom work to the 4.1 scan loops.

The important distinction is that these did **not** all remain fork-owned.

## What remained fork-owned

The native extraction architecture continued to evolve on the perf branch and is still the main reason the branch exists:

- reusable/batched native FFmpeg decoding;
- D3D11 32x32 gray-byte scaling before GPU-to-CPU transfer;
- the D3D11 VideoProcessor gray-byte path;
- capability/family-scoped hardware fallback and adaptive D3D11 policy;
- native health and detailed extraction telemetry;
- native AI frame extraction and the compatibility layer around the custom engine;
- hardened process fallbacks for cases where the native engine cannot safely handle a file.

`57d583a` later split the growing FFmpeg engine into native-health, telemetry, and hardware-policy partials and added the JSON regression probe. Those architectural/tooling changes remain part of the maintained perf branch.

## What upstream absorbed

Several features that were present in the early 4.1 perf port are now **upstream-owned** and must not be maintained as duplicate fork implementations:

- CPU-bound matching headroom / `MatchingMaxDegreeOfParallelism` — upstream `99ddb67` explicitly adapted the fork implementation.
- pHash required-sample quorum — upstream `f55f25d` explicitly adapted the fork feature, and `10b5fa1` subsequently refined its averaging, quorum precomputation, CLI handling, and tests.
- comparer zoom/pan/swipe/mode/stale-frame fixes — upstream `721e77e` explicitly adapted the fork work.
- anamorphic/SAR-correct display thumbnails — upstream `3aced4b` explicitly adapted the fork work.
- reverse-proxy/auth hardening — upstream `c8edaf3` explicitly adapted the fork work.
- per-position native timeout and software-frame hardware-transfer guard — upstream `2761177` explicitly adapted the fork work; the perf branch preserves those semantics inside its more specialized decoder.

The old matching-concurrency implementation and duplicate pHash tests have therefore been removed from the perf branch. The only remaining `ScanEngine` pHash difference is a semantically equivalent hot-loop optimization: it precomputes the strict Hamming threshold once and uses direct `BitOperations.PopCount` per sample.

## Compatibility phase

Once upstream began absorbing the fork work, the branch increasingly became a compatibility carrier around its custom FFmpeg engine. Commits such as `d1e77c` reconciled upstream's adopted performance changes rather than introducing a new competing implementation.

The July AI compatibility series (`3796131`, `f155568`, `f5a4e82`, `40c3000`, and related follow-ups) evolved into the current `FfmpegEngine.AiCompat*` partials. Those remain necessary because upstream AI call shapes must work against the fork-owned native engine.

Later upstream decoder-safety fixes are maintained as explicit parity bridges rather than treated as fork features. The refresh workflow preserves the custom engine on conflicts, applies the parity/safety reconciliation layer, then runs the entire reconciliation layer a second time and rejects any second-pass diff.

## Current state

The branch now intentionally consists of:

1. upstream 4.1 application/UI behavior inherited from `master`;
2. the fork-owned native/D3D11 extraction engine;
3. explicit upstream correctness bridges around that engine;
4. extra pathological-media/native-FFmpeg regression coverage;
5. a pinned same-run performance-regression gate;
6. GUI-only Windows x64 Native AOT release automation.

The old 4.0 DataGrid and monolithic MainWindow customizations remain intentionally excluded.
